# 系统文档模板

发现符合 [维护规则](../maintenance.md) 收录标准的独立新系统时，将下面结构用于 `systems/<system-name>.md`；已有系统优先修订原条目。一次实例操作完成不触发新建文档。这是模板，不是游戏事实；删除填写提示，未核实内容明确写“未知”。

每份系统文档开头写清已验证的环境、玩法范围和解锁条件；避免依赖过去聊天上下文的模糊指代。

以独立目标组织玩法路径；章节顺序、任务导航、计数、任务奖励、教程串联和回任务栏步骤全部放在onboarding.md；玩法文档不保留条件式主线步骤或章节目标示例。新模块新增文档，已有模块补充条目。仅记录实际体验或用户直接确认的玩法规则；辅助理解资料不摘录进知识库。

## 系统名称与用途

说明玩家为何使用这个系统，以及它在整体游戏中的作用。区分当前已知与推测。

## 入口与识别

记录入口名称、所在页面及可见识别特征；不记录固定坐标。解锁条件已明确时写入，未知时标为未知。

## 可复用操作路径

从用户可能提出的单项目标出发，按“当前可见入口 → 目标页面 → 关键操作 → 完成画面”的顺序写步骤。每一步注明需要在现场核对的名称、条件或材料；写清成功信号、失败或锁定时的分支，以及达到目标后的停止点。只纳入已实际操作或界面明确说明的路径，不记录固定坐标，也不把某次账号进度写成通用前置。

## 操作与系统关系

概述输入、操作、结果、成本、次数/队列/计时限制，以及与其他系统的依赖关系。每个重要机制链接到下面的条目，让操作步骤和界面判断点能够自足。

## 知识条目

### 描述性结论标题

- 状态：已观察 / 已验证 / 用户提供规则 / 推测 / 有争议 / 已失效，按证据选择。
- 结论：一条可独立核对、范围明确的规则。
- 界面判断点：未来执行时能看到的文字、状态或操作前后变化；不要用预期结果充当实际结果。
- 解释：为什么这些界面判断点支持结论；推断要显式说明。
- 适用范围：环境/构建、账号阶段、前置条件、特权；未知项标明。
- 最后核实日期：实际核实日期。
- 相关问题或条目：相关问题、依赖的知识标题及对应文档章节链接。

## 待解问题

链接 `../questions.md` 中相关问题，不在两个文件复制维护完整问题记录。

## 修订记录

记录条目状态或结论的重要变化及原因，不链接本机运行产物。模板本身没有实际知识条目和验证日期。
