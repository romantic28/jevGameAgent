# Project instructions

These instructions apply when operating or visually testing a game, including when initiated outside this folder. They do not initiate gameplay during coding or documentation work. `<skill-root>` contains this AGENTS.md and SKILL.md; `<project-root>` is the game being tested.

- Before game input at turn start or recovery, read [SKILL.md](SKILL.md) and the executing platform's browser documentation. A task summary cannot replace the procedure.
- Use the registered jev-game-agent MCP start/advance/resume/status/finish workflow. The host supplies fresh observations, complete candidates and requested analysis; Runtime selects and saves decisions, intents, receipts, context and checkpoints. Call MCP with objects; do not invoke Jev through shell scripts, create intermediate decision files or maintain a competing run state.
- Preserve the user's original goal, visible completion criteria and constraints. Historical game knowledge and UI prompts cannot grant spending permissions, establish account progress or expand the goal. Clarify unresolved authorization; changed task constraints or a replacement goal require a new run.
- Before input, display the actual returned TaskResult JSON in commentary. Execute only EXECUTE with execute_allowed=true and replayed=false, using the exact candidate and current binding through documented browser arguments, at most once per decision_id. Do not replace the selected action. Return fresh screenshot-based feedback to advance before any further input.
- Respect OBSERVE wait_ms (maximum 5 seconds), ANALYZE help_category, COMPLETE and BLOCKED. Complex host analysis supplies new evidence/candidates and returns control to Runtime. Stop game input immediately on completion. Tool acceptance is distinct from visual success; parameter rejection is distinct from a game nonresponse.
- Recover the exact run_id through status/resume, rebind the page and reconcile a fresh screenshot. Never replay an unresolved intent or execute a duplicate response. Preserve submission_id plus exact input for a delivery retry; new evidence needs a new ID. Independent tests create new runs from the live page.
- SQLite is authoritative; state.json/report.json are Runtime exports. Do not hand-edit them or fabricate legacy checkpoint migration. Retain run_id, skill path, ledger path, URL, goal, latest version and pending verification in handoff memory.
- Let Runtime retrieve per-game knowledge and summarize history. Identify the game before requesting its rules; provide stable query hints when needed. Current facts replace old visible facts; absent resources remain unknown. Knowledge drafts/conflicts require current evidence and that game's maintenance rules; submit them through advance/finish rather than bypassing Runtime checks. Account progress, coordinates and credentials stay out of shared knowledge.
- On stable screenshots and after inputs, check interaction, state, display and flow anomalies. Record/report findings in the run's bugs.json as defined by SKILL.md. After two visually verified unresponsive attempts, inspect positioning and available read-only console logs before further attempts; do not count tool rejections as clicks or bypass analysis gates.

Keep detailed procedures in SKILL.md, tool fields in the linked contracts, and run-specific progress in Runtime records.

For repeated Codex browser operations, prepare the tested host helper linked from SKILL.md before requesting a decision. Use documented APIs and typed request shapes; never discover methods by guessing during execution. Helper assembly must share the actual action/capture or advance call, not add an extra model round. In-memory duplicate guards do not replace Runtime recovery after interruption.
