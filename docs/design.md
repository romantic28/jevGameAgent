# Codex × Jev 双模型视觉游戏 Agent

状态：协作设计草案，待评审；尚未实施。2026-10-12。

## 1. 目标与设计起点

用户给出网页游戏预览 URL 和测试目标，Agent 自主完成观察、选择、操作、验证与停止，并记录沿途缺陷和有证据的游戏知识。自主指运行过程中无需用户逐步指挥，也无需 Codex 手工编排数据文件；不等于每轮都不调用 Codex。

保留原 gameAgent 已验证可用的截图测试方法。Codex 是视觉理解和生成能力提供者，Jev 是根据上下文作有限选择的决策能力提供者。先明确两者交换的内容和决策权，再选择工具通信及运行载体。本方案不要求游戏源码、专属状态接口、视觉检测器或每款游戏一套控制程序。

目前 Jev 仅接受文字。只要新的画面信息仍来自截图，就需要 Codex 将画面转成可判断的信息。首版接受这一成本，优化目标是减少决策生成和机械编排开销，整体是否提速通过实测判断。

## 2. 两种智能的职责

### Codex：看懂、解释、生成可供选择的表达

常规观察时，Codex 输出当前页面、可见对象与状态、数值、上次动作后的实际变化、不确定项和可执行选择。相同页面的稳定含义可沿用，变化信息须由新画面确认。输出应短，不附带推荐、排序、长篇推理或完整后续行动计划。

复杂分析时，Codex 解释陌生机制、补充缺失候选、重新定位目标、分析异常和形成知识草案。它可以提出多种路径及各自已知条件；正常情况下，下一步采用哪条路径仍由 Jev 选择。

候选生成不可完全中立，但必须可审查：保留与任务有关的可行替代项，标记前提未知的选项，不因“看起来不优”而提前删除。候选文字描述操作、条件和已知效果，不写“最佳”“应该立即”等暗含推荐的评价。明确禁止或不可执行的操作可以排除，并记录排除依据。

### Jev：判别局面、选择下一步

Jev 在当前证据和用户目标下选择完整动作，也可在有需要时选择阶段方向。它还可以选择等待、补充观察、请求机制分析、请求重新定位或结束任务。不要求它生成解释、工具参数、计划文本或知识文档。

阶段方向不是每轮必问。只有遇到需要路线权衡、当前方向受阻或前提变化时才判别；简单页面直接选择动作。新方向如果需要新增候选，由 Codex 补充后再选择，不能假设同一请求内的问题能读取彼此答案。

Codex 不例行复审并重选 Jev 的动作。返回选项不属于候选、违反明确约束、证据已失效等情况由确定性检查拦截。若必须由 Codex 接管，显式记录原因、范围与动作来源，后续恢复由 Jev 选择。

### 支撑层：机械工作自动完成

上下文保存与更新、差额计算、历史裁剪、知识检索、请求构造、答案关联、日志、执行状态和失败计数由支撑层完成。它不另设一套隐含的游戏策略来覆盖 Jev。

这里仅确定职责，不提前固定 Python、MCP 或浏览器实现。若后续采用 Python，它应主动维护状态并驱动生命周期，而非只给 Codex 提供读写文件命令。

## 3. 一轮协作如何发生

1. 获取当前截图及上一次工具执行结果，交给 Codex 的常规观察能力。
2. Codex 一次提供画面事实、变化、未知项、对象与操作候选；上一动作的视觉验证合并在这次观察里，不重复看同一张图完成两份工作。
3. 支撑层自动更新工作上下文，关联执行结果，加入当前必要知识，生成 Jev 请求。
4. Jev 返回离散选项和概率。结果进入对应分支：执行动作、等待后观察、补充理解或停止。
5. 执行动作后自动获取新证据，进入下一轮。动作已提交不等于成功；等待也有边界，不能无限轮询。

控制流程自动衔接。正常一轮不要求 Codex 创建 observation.json、prepared.json、submitted.json 等文件，不要求它保存 Jev 原始回答，也不要求它把 Jev 的答案重新改写成另一份决策。

工具由哪个宿主调用需要在技术设计中验证。若现有 computer-use 只能由 Codex 调用，允许保留该必要调度，但应直接执行 Jev 的选项，不重新作策略推理。不能把“仍需宿主调度工具”包装成已实现脱离宿主的后台自主运行。

## 4. 两个模型交换什么

### Codex 提供的观察包

最小内容为：画面引用、页面身份、可见事实、未知项、与上一轮的变化、交互对象、完整动作候选、异常线索。候选必须能关联到本次画面的可执行操作。动作位置属于短期执行信息，不进入长期游戏知识。

事实与解释分开。例如“按钮灰色”是观察；“可能因为挑战次数不足”是解释；“次数文字看不清”是未知。Jev 不能从一条未标记的猜测中得到虚假的确定性。

语义目标和候选可跨轮复用，坐标与当前可用性不可凭历史直接复用。新页面、新遮挡或布局变化使旧执行位置失效。

### Jev 收到的决策包

- 任务：原目标、完成条件、约束；不夹带推荐路径。
- 当前局面：新观察、对象状态、关键资源、未知项。
- 当前方向：仅在已选择且仍有效时提供。
- 相关反馈：上次动作及实际结果、当前受阻事项、有关历史失败。
- 必要知识：解释当前选项所需的游戏规则及证据状态。
- 选择空间：本次有限选项，每个选项描述完整操作与适用前提。

请求问题表达“依据这些信息选择什么”，不能只靠字段名暗示含义。目标、对象和条件需要在请求内自足，Jev 不依赖 Codex 的会话记忆。

### Jev 返回的决策

保留选项、概率分布、confidence、来源观察和所用上下文版本。选项映射到当前候选，不把返回值当作自然语言命令解析。不能把选项概率视作行动成功率，也不能伪造 Jev 的选择理由；需要展示时显示它实际选择的动作及证据引用。

## 5. 上下文的生命周期

工作上下文分为四部分，各自更新：

1. **任务记忆**：目标、约束、完成标准；只有用户变更目标才修改。
2. **当前局面**：新观察替换旧画面事实；未重新看见的信息标为历史已知或未知，不当作当前可见。
3. **行动反馈**：选择、提交、实际结果分开；保留尚未验证的动作，不能因中断自动重试消费、领取或战斗操作。
4. **游戏知识**：按游戏隔离的机制和操作经验；账号等级、资源和当前进度仍属于运行上下文。

默认给 Jev 最近 6 条已验证结果，同时保留更早但仍相关的阻塞、未满足前提和失败摘要。不能因为固定窗口而遗忘“这条路线刚刚失败”的信息。成功恢复后解除旧阻塞，不让历史失败永久禁止操作。

知识按当前页面、选项含义与未满足前提检索。关闭公告不加载整套迷塔攻略；迷塔编队才加载队伍与挑战相关知识。执行日志和完整知识文档留在外部，模型只收到本次判别必需的部分。超出输入预算时先去掉无关历史，不能静默丢弃约束或关键未知项。

机械数据增量自动合并；新的机制解释或知识冲突交给 Codex。Codex 形成知识草案，依据画面或已验证结果更新知识；Jev 的选择本身不构成事实依据。无需每轮额外调用 Jev 决定是否写知识。

## 6. 不确定时如何合作

区分三类情况：

- **多个选择都可接受**：可继续采用 Jev 所选的、满足约束的可逆行动；低 confidence 不自动触发复杂分析。
- **关键证据缺失**：选择重新观察，或要求 Codex 补充明确缺失的信息；不对相同输入反复请求更高 confidence。
- **表达能力不足**：现有选项没有合理解法、陌生机制、证据冲突、连续无进展，交给 Codex 生成新理解或补充候选，再交回 Jev。

帮助请求使用有限类别，例如重新定位、读取不清文字、解释机制、补充路径、分析异常；附当前未知项和失败证据。Jev 不需要生成自由文本求助理由。

confidence 门槛通过回放校准，不把上一版 0.4 设成所有行为的统一闸门。目标完成须有对应视觉证据；Jev 选择停止但证据不足时先核验。出现明确完成证据后不继续挑战下一层或推进下一章。

截图或工具失效等确定性故障直接暂停动作，不必先调用 Jev 判断故障是否存在。连续两次经核实的无响应触发现有定位核验与可用控制台检查，不能自动定性为游戏缺陷。

## 7. 用雾隐迷塔说明分工

以下是协作示例，不代表本轮已经执行实测，也不把既有账号进度作为新运行事实。

用户目标：完成一次迷塔挑战。开始前明确“到一次结算即完成”还是“必须胜利”；不能把用户的一次挑战自动扩展成无限重试。

- 公告页：Codex 给出弹窗与关闭对象；Jev 选择关闭方式；不加载全部迷塔知识。
- 主城页：Codex 识别当前入口及遮挡；提供进入地下城、查看相关入口信息等可用选择；Jev 选择。
- 迷塔页：Codex 读取当前层、可挑战状态与按钮；Jev 选择挑战或补充观察。
- 编队页：Codex 提供已有队伍、可见数值与替代操作；Jev 选择开始战斗、调整队伍或查看信息。Codex 不预先写“战力足够，立即开战”。
- 自动战斗：Codex 描述战斗仍在进行、是否有弹窗或结果；Jev 可选择等待。等待后仍需新截图验证。
- 结算页：Codex 提供胜负、层数、奖励及完成证据；根据任务完成标准结束，不自动点击下一层。

如果两次点击入口都未生效，反馈进入下一轮。Jev 可以选择重新定位；Codex 分析最新画面并补充对象，随后继续由 Jev 选择。无需用户逐步指导，也不让 Codex 管理中间文件。

## 8. Jev 接入原则：先消除调用摩擦

官方接口使用 `POST https://api.typesafe.ai/v1/systemone`，输入 `model`、`state`、`questions`，使用 Bearer key；Choice 返回有限选项。建议实现时采用官方 SDK 的长生命周期客户端，自动构造请求及记录结果，避免每次决策新起命令与连接。具体锁定的 SDK、模型版本在实现前核验并写入运行元数据。

正常请求不经聊天消息、终端交互输入或人工文件交换。独立问题可以共享状态一起调用；有前后依赖的问题分次处理。默认直接选择完整动作，避免每次固定执行“判断阶段→判断类别→选择动作”的额外调用链。

网络权限是运行载体的问题。不能宣称换成 MCP 或 SDK 就自动获得联网权限，也不能绕过宿主审批。技术验证时须先选定固定调用入口、确认该执行环境能读取配置的 key 并访问 TypeSafe；在宿主允许的授权机制下完成必要授权。若只能逐次批准，该载体不满足无缝运行要求，必须在进入游戏前暴露问题。

验收要求是同一入口连续多次真实文本请求，无逐次审批、无“先沙箱失败再重试”的常规路径。区分权限/DNS/TLS/代理、认证、请求格式、限流及服务故障；不能把所有异常统一写成 Jev 不可用。只对暂时故障有限重试；网络重试不能重放游戏动作。key 不进入模型上下文、日志或仓库。

运行期间决策服务持续不可用时暂停游戏动作并报告；不静默让 Codex 完成全部选择，掩盖双模型链路失败。是否启用显式 Codex 接管由运行策略决定，并单独计数。

## 9. 原 skill 如何迭代

保留“新截图→决策→操作→新截图验证”的逻辑顺序及缺陷检查。原来每次由 Codex 手写可见决策 JSON、逐步更新 checkpoint，是旧流程要求，可以随接入迭代。

新流程由系统自动展示和保存实际 Jev 决策与执行结果；Codex 只在关键变化、异常或任务完成时说明。日志内部采用何种文件格式不影响模型使用方式，不能再让文件格式变成模型的操作协议。

截图验证可以同时发现交互、状态、显示和流程异常。错误定位、工具失败、游戏疑似缺陷分别记录。知识维护和测试报告继续复用现有规则，在任务结束前完成整理。

## 10. 如何判断这套协作有效

先用既有运行记录重建有证据的场景，缺失截图或逐步候选的部分必须标为模拟，不伪装成原始完整回放。覆盖公告关闭、建筑重新定位、资源不足、多个合理选项、自动战斗等待、奖励后资源变化、章节完成停止。

检查四项核心能力：

1. Codex 的输出不包含推荐动作；Jev 能在多个真实候选间作选择，并随新证据改变选择。
2. 删除不相关知识不影响理解；保留相关失败后避免无意义重复；新截图覆盖旧状态，未验证动作得到核对。
3. 复杂分析只处理缺失理解，之后交回 Jev；常规视觉观察次数与复杂分析次数分别统计。
4. 连续运行无需用户逐步操作或 Codex 创建中间文件；目标达到即停。

之后使用同一游戏、相近起始状态与目标比较纯 Codex 和双模型运行。记录观察耗时、Jev 往返耗时、工具耗时、编排开销、总耗时、输入量、完成率、无效动作和接管情况。Jev 几十毫秒的局部速度不能代替端到端结果，当前不承诺整体提速比例。

本轮交付止于协作方案。进入实现设计前，下一步只需验证运行载体如何连续调度 Codex 的截图能力和 Jev 请求，以及如何消除逐次审批；不重新扩张为专用视觉服务或每款游戏的控制工程。
