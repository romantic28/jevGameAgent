## 预期与实际结论

预期是让 AI 持续观察游戏、执行操作、验证变化并发现异常；Jev 应提供有价值且快速的判断，整个操作循环应足够快，具有相对原有纯视觉执行方式的实际收益。

实际实测主要限于“打开真实游戏预览页 → 关闭欢迎公告 → 确认标题/服务器页”。没有登录、进入游戏或完成持续玩法任务，没有完成迷塔和建筑拖动等原计划验收。局部任务 COMPLETE 只证明这项关闭公告任务成功，不代表整个游戏测试工作流验收成功。

用户反馈：这样的速度和交接成本不适合让 AI 玩游戏并测试，使用体验不如原来的纯视觉执行。该反馈作为本次效果结论保留。未在相同条件下完成纯视觉基线的对照测试，因此不能给出新方案相对旧方案的精确速度比或全面优劣结论。

## 问题根源与失败原因

当前分工是：Codex 看图、识别目标、生成候选 → Runtime/Jev 选择 → Codex 阅读回答、展示 JSON、发起浏览器输入 → Codex 看新图、组织反馈 → Runtime 保存并再次判断。

对于关闭公告这种明确的单步操作，Codex 已承担主要视觉与定位工作，Jev 的候选选择增加了一次交接，却没有卸载随后执行和反馈的模型处理。每个工具边界还要经过宿主模型组织调用、输出以及平台调度。修正 API 与参数错误后，仍出现约 8.26 秒和 6.54 秒的交接间隔，说明“接口正确”不足以让循环变快。

这些间隔是观察到的整体宿主交接时间，现有记录不能将其进一步精确分解为模型推理、文本生成、排队、工具投递分别耗时多少。不能据此宣称每一秒都是模型思考。

辅助函数提高了固定步骤的可靠性，但截图和反馈仍跨 CUA 与 MCP 两个独立入口；模型还需解释新图片。仅减少说明文字、增加 SKILL 提醒、把参数组织封装为函数，都没有改变这一架构限制。

另有两个实施局限：最新实测浏览器侧通过手动转写函数加载到 REPL，并非证明仓库脚本按原文自动加载成功；运行中的 MCP 工具描述仍是旧描述，新增说明尚未因源码修改自动刷新。最新实测证明的是该调用路径可执行，不能宣称整套部署和自动装载已经验收完成。

## 未达到的验收项目

- 连续多步玩法的完成率、吞吐与长时间稳定性。
- 相对原有纯视觉执行方式的同条件收益。
- 在真实持续玩法中发现异常、形成证据并复现的能力。
- P3 的迷塔挑战、建筑搬迁等验收；P4 优化也没有完成。
- 消除或显著压缩每轮模型交接成本。

局部目标完成、快速 Jev 请求、模块自动化通过，都不能覆盖这些未达到的目标。

## 后续决策

保存实验，不合并 main；暂停在本串行方案上继续叠加补丁。若另行启动重设计，应先保留纯视觉连续执行作为基线，确定 Jev 有实际收益的判断场景，再比较连续任务总耗时、完成率和异常发现能力。

考虑让程序自动保存截图、回执和性能记录，并对明确操作缩短视觉到执行的路径。Jev 可评估按需用于优先级、路线、资源取舍和异常分类等选择，但这些是后续候选方向，尚未实现、尚未验收。自动提交截图与输入回执不能自动产生可靠的视觉成功结论；视觉判断仍需有明确实现。

本记录不授权开始下一阶段、不修改主分支、不宣称实验已经满足 AI 游戏测试目标。
