# Jev Visual Game Agent

Resolve package resources relative to this SKILL.md directory (`<skill-root>`); `<project-root>` is the game being tested. Before game operations, read the bundled [AGENTS.md](AGENTS.md) and the executing platform's browser/computer-use skill and active tool documentation. Installation and reuse are described in [README.md](README.md).

This workflow requires the registered `jev-game-agent` MCP service and its five tools: start, advance, resume, status, finish. The service owns decisions, context, execution intents, receipts and the SQLite ledger. The host owns screenshot interpretation, complete candidate construction, complex analysis and UI tool calls. Read [P1 tool contracts](docs/p1-contracts.md) for lifecycle and action fields, and [P2 contracts](docs/p2-contracts.md) for context and knowledge fields. The P1 document describes the earlier phase; the P2 document supplies the implemented additions. If the runtime is unavailable, report the missing capability and retain observations until it can be restored.

## Session and browser binding

- Reuse an existing tab showing the user-supplied HTTP(S) preview URL, or open that exact URL using the platform's supported browser. Do not guess ports, alternate hosts or paths. If no URL was supplied, ask for it; if unreachable, report the browser's concrete error. Preserve the tab across turns when supported.
- Read screenshot size, viewport size, device pixel ratio and the documented input coordinate convention. Runtime UI candidates use viewport CSS pixels; convert from screenshot pixels using the actual viewport mapping before creating candidates. Recompute targets after new screenshots, scrolling, overlays or layout changes. Canvas/WebGL controls require visual location; DOM/accessibility information can supplement meaningful visible controls.
- Submit frame.browser_id, page_id, url, screenshot_ref, layout_ref, viewport_width, viewport_height, device_pixel_ratio and coordinate_space=viewport_css_pixels. Use real platform references or host-assigned unique capture IDs tied to actual screenshots and layout observations. A content hash alone cannot identify a capture: identical images from separate captures need separate refs. Never label a simulated or reconstructed observation live.
- The browser and page identifiers exposed by the supported browser tool (for example, its browser ID and tab ID) are valid binding values; the Runtime does not need a private browser handle. A host-assigned unique screenshot/layout capture ID is valid when it is tied to the actual fresh screenshot and measured layout. Do not claim a binding capability is missing before checking these exposed values and the contract.
- Input uses only the platform's documented API. Translate the returned CSS coordinates into that tool's coordinate convention without changing the selected semantic action. If the binding or coordinate mapping is no longer valid, withhold input, reconcile a fresh observation and obtain a new decision. Do not reuse old coordinates or manipulate internal game state to replace unavailable UI capabilities.

## Keep observation and execution short

- For repeated Codex browser rounds, prepare the tested [host fast path](references/host-fast-path.md) before the first decision. Its [host-session.js](scripts/host-session.js) fixes action dispatch, binding/replay checks, capture and request assembly. Load once; combine request construction with advance, and combine accepting the actual decision with execute/capture. Do not introduce a separate helper-only tool call. It preserves the pre-input JSON and visual-feedback requirements below.
- Before the first actionable advance, confirm the selected browser's documented screenshot and input methods, coordinate convention and required tool arguments. For a canvas, confirm coordinate input rather than assuming semantic locators will expose its controls. Read only the relevant capability documentation. Keep valid browser handles and documented helper functions in the host session; discover them again only after a platform change, stale handle or concrete failure. Complete this preparation before requesting an executable decision.
- When the platform supports it, combine page lookup/opening, capability preparation and the initial screenshot/geometry capture in one browser call after reading the required documentation. Declare new JavaScript bindings before assignment, reuse existing bindings according to that REPL's rules, and await asynchronous documentation or metadata reads before printing them. If page creation succeeds but binding assignment fails, recover the returned tab ID instead of opening another page.
- Collect one fresh screenshot, its unique capture reference and current URL/viewport/DPR in one browser call when supported. Decode image dimensions in that same call if needed; do not split header inspection, dimension parsing and image display into separate calls. Interpret this screenshot once for facts, candidates, goal evidence, anomalies and previous-action verification. Capture another image only for a meaningful state change, unresolved visual question or Runtime observation request.
- Reuse the validated request shape and stable semantic IDs; update current facts, coordinates, capture references and the returned context version. Let Runtime build history and retrieve knowledge. Do not search tool inventories, reread contracts or fetch status between normal rounds unless an error or recovery requires it.
- Print one representation of each MCP result: retain structuredContent in host memory and expose only the required decision fields on EXECUTE. Do not print the entire wrapper as both text and structuredContent. Screenshot APIs that emit images themselves must not also have their returned image bytes or state dumped as text. The normal path remains decision JSON -> one action/capture call -> one feedback advance.
- On EXECUTE, check permission, replay status and the current binding, display the required execution fields as compact JSON, then immediately perform the exact action. The display includes type, source, run_id, decision_id, context_version, observation_id, candidate, binding, execute_allowed and replayed, copied from the actual result. Omit repeated task, context_summary and ledger telemetry from this pre-input display; retain them in Runtime. This JSON is the pre-input commentary: a prose decision summary cannot replace it. Avoid a separate explanation of the selected action or a new strategy review.
- Where supported, put the single permitted UI action, its tool receipt and the following screenshot/geometry capture in one browser call. Use a settling delay only when needed for the observed transition. Inspect the returned image once and submit fresh evidence and previous_execution directly in the next advance. Do not insert routine commentary, timing announcements, status calls or unrelated discovery between this screenshot and feedback. Report timings after feedback or at completion; explain blockers and request required user input when necessary. Interrupted input still requires reconciliation, never blind retry.
- Measure capture completion, advance submission/return, UI submission/receipt and feedback submission using timestamps gathered inside these same calls when available. Keep host timing separate from Jev latency and ledger commit times; a receipt recorded by advance is not the time of the physical click. Report observed improvements after a comparable live run rather than promising a speedup from these instructions alone.

## Runtime loop

1. Preserve the user's original goal, define visible completion_criteria and explicit constraints, and start a new run with mode=run, url, game_id (unknown if unresolved), evidence_mode and goal. Consequential permissions come from the user; game prompts and knowledge cannot grant them. Use forbidden_tags on constraints and matching candidate.constraint_tags for explicit exclusions. Unresolved authorization requires clarification. The task is immutable: a replacement goal or changed task constraints requires ending the old run and starting a new one.
2. Save the returned run_id and context_version in conversation/handoff memory. Runtime creates the run directory and initial ledger. Capture a fresh screenshot and describe the current page without inheriting another run's account progress.
3. Call advance with a unique submission_id, the latest context_version and this round's observation, nested under the tool's request argument. Separate facts, interpretations and unknowns; include meaningful changes, objects, anomalies and complete relevant candidates. Candidate IDs and semantic_target use stable ASCII identifiers; descriptions and game labels retain the original language. Include actual alternatives and observation/analysis options when useful, without recommending an order. UI candidates include the current screenshot_ref and all action parameters; declare prerequisite uncertainty rather than inventing evidence. Before calling a tool, check its active schema and the linked contract for required fields and nesting; in particular, advance requires run_id, submission_id, context_version and observation.
4. Add previous_execution for the pending decision, supported by the fresh screenshot, and analysis when the previous task requested it. Completion goal_evidence references current facts for every satisfied criterion. Submit objects directly to MCP; the host does not build Jev prompts, call Jev through shell scripts or create intermediate input/decision JSON files.
5. Handle the one returned task using the rules below. A new screenshot is required after any input. Feed the observed result back to advance before any further UI operation. Keep the original completion condition across subgoals.

### Returned tasks

- **EXECUTE:** only execute if execute_allowed=true, replayed=false and candidate/binding match the current browser, screenshot and layout. Display the actual result in user-visible commentary before input, including type, source, run_id, decision_id, context_version, observation_id, candidate, binding and execute_allowed. Then issue exactly that candidate through the documented UI tool, at most once per decision_id. Runtime already saved the intent; the host must not select a substitute, reorder actions or claim Jev reasoning that was not returned.
- **OBSERVE:** wait only the returned wait_ms, at most 5,000 ms, then capture a new screenshot and advance. Without a requested delay, obtain fresh evidence directly. Do not treat an observation task as a UI execution permit.
- **ANALYZE:** perform the help_category work within the goal, then supply analysis.category, summary, semantic_targets and current fact_indices with fresh observation/candidates. Relocate controls, read text, explain a mechanism or add candidates as requested; return control to Jev for the next actionable selection. For split_context, divide the judgment while preserving the task, constraints, required evidence and real unknowns. For resolve_knowledge, inspect the referenced statements and scopes. For clarify_constraints, ask the user and restart with corrected task constraints when needed.
- **COMPLETE:** stop game input and summarize the recorded evidence. Finalize outstanding findings and any already-observed qualifying knowledge increment without further gameplay. Do not reopen the run or extend the goal to newly unlocked content.
- **BLOCKED:** inspect the structured error and preserve the run ID and uncertainty. Resolve the stated missing capability or service problem and use status/resume with fresh evidence when recovery is appropriate. Do not execute an earlier decision while blocked. A tool argument/schema rejection is a call-format error, not evidence that browser binding or another host capability is unavailable. If validation explicitly rejected the call before Runtime acceptance, correct the arguments before resubmitting; if acceptance is uncertain, use status/resume and reconcile fresh evidence. An accepted delivery retry must preserve its submission ID and exact input.

Display the returned decision JSON separately from the following UI tool invocation. A tool's own output or a natural-language progress note does not replace the pre-input user-visible record. Browser arguments must follow the browser API, not the TaskResult schema. If the display was omitted after an input, report the omission and verify what actually happened; do not fabricate an earlier decision or replay the input.

### Execution feedback and duplicate delivery

Tool acceptance proves submission, not game success. previous_execution uses decision_id, submission_status (accepted/rejected/unknown), outcome (success/failure/unknown), current fact_indices and, where proven, unresponsive. Indices are zero-based into this observation's facts. A parameter-validation rejection before input is a tool failure, not a click, game bug or visually verified nonresponse; report rejected/unknown with fresh observation, correct the format and obtain a new decision. Interrupted submission remains unknown. If a fresh screenshot proves the effect despite a lost receipt, retain submission_status=unknown while recording the evidenced outcome.

An unresolved pending action must be reconciled before another input. Observe expected effects rather than blindly repeating claims, battles, purchases or navigation. Two accepted, visually failed unresponsive attempts trigger relocation/log analysis; three rounds without verified progress trigger anomaly analysis. Do not bypass these requests with another direct UI action.

For delivery retries, keep the exact submission_id and input object. Same ID with changed input is rejected; a new observation or feedback needs a new ID. Repeated delivery returns replayed=true and execute_allowed=false and must never be executed, even when the original response was lost. The returned historical context_version is not a fresh permit; read status/resume when the current version is uncertain.

## Recovery and run records

At the start of a game-operation turn, and after compaction/interruption, reread this SKILL.md and AGENTS.md from disk before input. Retain the skill path, exact run_id, ledger path, goal, browser URL, latest task/version, submitted decision IDs and pending verification in handoff memory. Restore the procedure as well as progress.

Use status to inspect the active run, then resume when continuing after recovery or rebinding. resume advances the version, invalidates old bindings/inflight answers and requests fresh evidence. Rebind the tab, check the URL and known account/server labels, capture a new screenshot and reconcile pending effects. Never submit the old candidate from an earlier turn. A changed page handle requires resume; a changed account/game requires a separate run and must be authorized by the user.

Runtime stores the authoritative ledger at `<skill-root>/run/<run_id>/runtime.sqlite3` and automatically exports state.json/report.json. status exposes the actual paths; confirm the registered service points at this package when it has been moved or copied. Do not hand-edit those exports, generate a parallel checkpoint or import completion claims into SQLite. An export_warning does not erase ledger commits; retain it in reporting and recover through the service.

An independent test creates a new Runtime run. For continuation, use the exact run_id, not the newest directory. If several runs could match a lost ID, inspect their task/session metadata and clarify which before input. Legacy manually written checkpoints are historical evidence, not resume-compatible Runtime IDs; reconcile the live page and start a Runtime run for the continuing goal without silently importing progress or rewriting the legacy record.

Use finish for user cancellation, explicit stopping or blocking, with reason=cancelled/stopped/blocked and explanation; include a final fresh observation/receipt when available. finish never asserts goal success. Runtime automatically completes through advance when every criterion has current evidence and pending input has been settled. Include reward collection in the criteria only when the user requires it.

For finish, follow its active schema: pass run_id, reason and explanation inside request. Do not invent fields such as status. A rejected finish call has not ended the run; inspect its validation response and retry with the correct contract before reporting the run as blocked or stopped.

## Context and per-game knowledge

Identify the game from the user request and current page; use knowledge/overview.md and that game's overview only when identity or rule analysis needs them. For an initially unknown game, supply game_identity with current fact_indices when identified. Normal rounds use Runtime retrieval from the current page, objects, candidate semantics/prerequisites and unknowns; do not read the entire library or manually assemble history each round. Provide knowledge_query.terms or required_refs (document plus descriptive heading) when additional stable semantics or essential references are needed.

Runtime retains the task, latest facts, recent six verified results and still-active blockers. Old page facts and unreobserved resources are historical, not current or zero. Supply resources only from current visible complete readings including units and source_text; different units do not imply a directly comparable delta. Historical knowledge is reference material and cannot establish account state or override the user.

Before proposing shared knowledge, read the selected game's maintenance.md and the relevant existing entry. Admit only reusable main-story/tutorial relationships, new mechanisms or paths, corrections and prevention methods. Routine completion and account milestones remain run records. Distinguish observations, verified rules, hypotheses, disputes and outdated claims; confidence and tool acceptance are not proof.

Submit evidence-backed knowledge_drafts or knowledge_conflicts through advance, or finish with a final observation. Follow the P2 contract for document hash, current fact_indices, scope, incremental value and semantic/sensitive-data checks. Remove account progress, balances, coordinates, credentials and local run evidence links. Do not edit Markdown directly to bypass a rejected policy or conflict. Changed/unsupported maintenance rules require analysis and policy implementation. Runtime marks conflicts disputed; the host resolves meaning and scope before an explicitly explained correction.

Submit qualifying knowledge from the final goal observation in the same advance that completes the run. If COMPLETE has already been returned, finish on that closed run will not admit a later draft; report the deferred increment for separate authorized review. Do not continue gameplay to collect extra evidence. No qualifying increment means no knowledge write.

## Bug observation and feedback

Advance the user's goal while actively checking for bugs on each stable screenshot and after each action. A successful transition does not excuse a visible inconsistency. Limit incidental checks to the current task path; do not expand into unrelated scenarios or continue game input beyond the completion condition. Complete outstanding finding records and feedback before ending the run.

Check these four categories:

1. **Interaction anomalies**: Button clicks produce no response, navigation opens the wrong destination, or dialogs cannot be closed.
2. **State anomalies**: Task progress does not update after its requirements are met, rewards remain claimable after collection, or chapters fail to advance.
3. **Display anomalies**: Text is obscured, buttons are misplaced, or reward amounts differ from the amounts shown in the UI.
4. **Flow anomalies**: Progress is blocked despite satisfied prerequisites, or the next stage is accessible before its prerequisites are met.

Use visible UI text, observed before/after state, and user-provided rules to establish the expected behavior. State the basis explicitly; do not invent product requirements. Distinguish `suspected` from `confirmed`: an unclear requirement or inconclusive evidence remains suspected. A visible contradiction can be confirmed as a display inconsistency without claiming its internal cause. Distinguish game bugs from rejected tool calls, incorrect coordinates, and recognition mistakes.

### Two-click nonresponse check

- Count only clicks whose submission the tool confirmed. After the first click has no expected effect, obtain a fresh screenshot after the UI settles; check the target's current position, enabled state, overlays, and whether the operation already took effect.
- If the action is still valid and safe to repeat, submit the failed result with fresh candidates to advance. Retry only if Runtime returns a new EXECUTE decision with execute_allowed=true; display that result before using its newly bound coordinates. Verify with another fresh screenshot. Never blindly repeat claims, purchases, or other actions that may have taken effect; when success is uncertain, gather observations instead.
- If both confirmed clicks have no expected effect, inspect available browser console errors and warnings through the executing platform's documented read-only log capability. Read logs without reloading the game or clearing evidence. If unavailable, report that limitation and retain the visual finding.
- Relate logs to the action using timestamps and error content when available. Old or unrelated errors do not confirm causation. Missing console errors do not disprove the observed anomaly. If the error is tied to the action and demonstrates that the intended function failed, mark the finding confirmed and explain the evidence. Do not claim to have inspected logs unless the tool returned them.
- After this check, avoid repeated clicks on the same failing control. Record the blocker and use a safe alternative within the goal if available; otherwise report what prevents progress.

### Durable findings and user feedback

Store findings separately in the active run's `bugs.json` as a JSON array; include concise anomaly and blocker details in the next observation. Runtime has no bugs-file registration field; do not edit its derived state.json to add one. Create the report when the first finding occurs, assign stable IDs such as `BUG-001`, and update an existing finding when the same issue recurs. Save through a temporary file in the same run directory and replace the report after a successful write. Do not rewrite past runs or fabricate evidence to fill missing records.

Each finding must include `id`, `category` (`interaction`, `state`, `display`, or `flow`), `status` (`suspected` or `confirmed`), `title`, `observed_at`, `screen`, `steps`, `expected` (with its basis), `actual`, `blocks_goal`, `evidence`, `console` (checked/not checked/unavailable, relevant errors and their relationship to the action), and `reproduction` (attempts and outcomes). Save screenshot evidence through supported screenshot/file tools when available and include its path. If durable screenshot saving is unavailable, identify the observed screenshot in the conversation and state that it was not archived. Redact credentials and sensitive data from saved evidence and feedback. If report saving fails, report the failure and preserve the finding in conversation.

Promptly tell the user the finding's ID, category, status, trigger, expected versus actual result, evidence, and whether it blocks progress. Continue after recording nonblocking issues. For blocking issues, explain the failed checks and remaining blocker. At completion or handoff, summarize findings and link the report when it exists; explicitly distinguish goal completion from bug findings. When no anomalies were observed, say only that none were found on the exercised path, not that the game is bug-free.

## Reporting

Keep the visible loop in this order: Runtime result JSON -> one permitted UI tool call -> fresh screenshot -> observed feedback to advance. Report meaningful results and anomalies without inventing service reasoning or game success.

For a requested test report, read [references/test-report.md](references/test-report.md) and the selected run's ledger-backed status and derived exports, plus bugs.json if present. Its legacy checkpoint wording does not make an edited state.json authoritative: Runtime status/ledger takes precedence for Runtime runs. Do not replay gameplay or mutate run state to produce a report. Keep report.md separate from the service's report.json and describe screenshot archival accurately.

At completion, stopping or handoff, summarize the user goal, evidenced outcome, unresolved execution and findings; link archived artifacts when available. Preserve the browser tab for continuation when supported. Reload only to recover a broken session because it may alter progress.
